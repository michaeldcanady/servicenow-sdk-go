External OIDC

External OIDC authentication signs a user in through your organization's third-party identity provider (external IdP), such as Microsoft Entra ID, Okta, Auth0, Google, or ADFS, and lets the SDK call ServiceNow on that user's behalf. The SDK acts as an OIDC client: it resolves the IdP's discovery document, runs an authorization code + PKCE grant as a public client, and presents the resulting token verbatim to ServiceNow.

The external IdP is the token authority for this flow, not ServiceNow. ServiceNow validates the token through an OIDP record; the SDK performs no token validation.

Objective​

Configure and use external OIDC authentication with the ServiceNow SDK against a standards-compliant OpenID Connect issuer, using values from your identity administrator and your ServiceNow administrator.

Required values​

Your identity administrator registers the application and provides:

ValueDescription
Client IDThe application (client) ID from the IdP app registration
Issuer URLThe IdP's issuer, or its full /.well-known/openid-configuration URL
Redirect URLMust match a redirect URL registered on the IdP app
Audience scopeOnly for an audience-scoped access token, for example api://{clientId}/.default on Entra ID

Your ServiceNow administrator configures an OIDP record with:

ValueDescription
Client IDMust equal the aud claim in the token the SDK presents
User claimA claim, such as upn or preferred_username, that maps to a sys_user record
Metadata URLThe IdP's OpenID Connect metadata URL; for Entra ID, use the v1 URL
JTI verificationOff when the IdP doesn't emit a jti claim, which Entra ID doesn't

SDK flow​

Set up the identity provider​

  1. Register an application in the external IdP, and add the redirect URL that the SDK's local listener uses. The default redirect URL uses port 5001; change the port with WithPort or supply your own redirect setup with WithServerFactory.
  2. For the default ID token path, grant the openid scope. Add an audience scope instead when you want an audience-scoped access token.
  3. Record the application (client) ID and the issuer URL for the SDK and the OIDP record.

Set up the ServiceNow OIDP record​

Create an OIDP record that trusts the external IdP, then set:

  • Client ID to the token's aud claim. For the ID token path, this is the IdP application (client) ID. For the access token path, this is the token audience, for example api://{clientId}.
  • User claim to a claim that identifies the user, so ServiceNow can resolve a sys_user record.
  • Metadata URL to the IdP's OpenID Connect metadata URL. For Entra ID, use the v1 URL; v2 access tokens don't validate.
  • JTI verification off when the IdP doesn't emit a jti claim.

Choose the presented token​

The SDK presents one token verbatim. Pick the path that matches how the IdP app and the OIDP record are configured:

PathConfigure withPresented tokenOIDP record Client ID
ID token (default)No scopes (scope openid)The ID tokenThe IdP application (client) ID
Audience-scoped access tokenWithScopes("api://{clientId}/.default")The user access tokenThe token audience, such as api://{clientId}

The SDK performs no token-type detection. It presents whichever JWT the configured scopes produce, and the OIDP record validates it.

Initialize the SDK​

Use the default ID token path when the OIDP record's Client ID is your IdP application (client) ID:

provider, err := credentials.NewExternalOIDCProvider(
	"{clientID}",
	credentials.WithInstance("{instance}"),
	credentials.WithOIDCIssuer("https://login.microsoftonline.com/{tenantID}/v2.0"),
)
if err != nil {
	log.Fatal(err)
}

client, err := servicenowsdkgo.NewServiceNowServiceClient(
	servicenowsdkgo.WithAuthenticationProvider(provider),
	servicenowsdkgo.WithInstance("{instance}"),
)
if err != nil {
	log.Fatal(err)
}

// Client is now authenticated and ready to use
_ = client

For an audience-scoped access token, add the audience scope:

provider, err := credentials.NewExternalOIDCProvider(
	"{clientID}",
	credentials.WithInstance("{instance}"),
	credentials.WithOIDCIssuer("https://login.microsoftonline.com/{tenantID}/v2.0"),
	credentials.WithScopes("api://{clientID}/.default"),
)
if err != nil {
	log.Fatal(err)
}

Troubleshooting "User Not Authenticated"​

ServiceNow returns User Not Authenticated (HTTP 401) when the OIDP record rejects the token. The SDK performs no token validation, so this response is always an OIDP configuration problem. Check these causes:

CauseFix
The OIDP record's Client ID doesn't equal the token's audSet the record's Client ID to the token audience: the IdP client ID for the ID token path, or api://{clientId} for the access token path
No user claim maps to a sys_user recordMap a claim that carries the user identity, such as upn or preferred_username, in the OIDP record
JTI verification rejects a token that has no jti claimTurn off JTI verification when the IdP, such as Entra ID, doesn't emit jti
The token is a v2 access token or an opaque tokenUse the Entra ID v1 metadata URL and an ID token or a v1 audience-scoped access token
The token is a client-credentials (machine) tokenMachine identity is unsupported through the OIDP; use the native Client Credentials grant

To tell the failure sides apart in code: a token the IdP couldn't issue surfaces as credentials.ErrTokenAcquisition, and a ServiceNow rejection surfaces as *core.UnauthorizedError, which matches errors.ErrNotAuthenticated through errors.Is.

IdP compatibility​

ServiceNow's OIDP record accepts either an ID token or a user access token, as long as the token is a JWT whose aud equals the record's Client ID. The table captures the per-provider specifics.

IdPAccepted tokenOIDP Client ID (aud)User claimNotes
Microsoft Entra IDID token (default) or v1 access tokenIdP client ID, or api://{clientId}upnUse the v1 metadata URL; Entra ID doesn't emit jti, so turn off JTI verification
OktaID tokenIdP client IDsubServiceNow publishes an Okta ID-token example
Auth0ID token or access tokenClient ID, or the Auth0 API identifiersubCustom claims require an Auth0 Action before they appear
GoogleID token onlyIdP client IDemail or subGoogle access tokens are opaque, so the OIDP can't validate them
AD FSID token or access tokenClient ID, or the AD FS resource identifierupn or emailBoth tokens are JWTs; no ServiceNow walkthrough is published

Sources​

  • ServiceNow docs, Configure an OAuth OIDC provider for accepting third-party token: the record verifies ID tokens; the Client ID must equal the aud claim; templates exist for ADFS, Auth0, Azure AD, Google, and Okta.
  • ServiceNow blog, Federated Token Authentication for ServiceNow API Access (Inbound): ServiceNow accepts either ID tokens or access tokens.
  • ServiceNow community, External OIDC provider with an inbound REST call: for Auth0, set the OIDP Client ID to the token audience, not the client ID.
  • Microsoft Learn, AD FS OpenID Connect/OAuth concepts: AD FS issues both an ID token and an access token as JWTs.
  • Google OAuth access tokens are opaque, not JWTs.
