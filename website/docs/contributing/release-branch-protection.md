# Release branch protection runbook

Workflow-level hygiene for `release/v*` PRs is enforced in-repo
(`.github/workflows/branch-policy.yml` now targets `release/**` too), but
the hard guarantees — no direct pushes, required reviews, protected history —
are admin settings outside Actions. They're declared in this repo as code
(`.github/policies/servicenow-sdk-go-branch-protection.yml`, #658, ADR 011
rule 3) **and** applied in GitHub as live settings so OpenSSF Scorecard can
detect them. The file is the reviewed source of truth; the live settings are
what Scorecard evaluates — both must stay aligned.

## How protection is applied (classic + ruleset hybrid)

Scorecard v5.5.0 (`ossf/scorecard-action@v2.4.4` in `.github/workflows/scorecard.yml`)
detects **both** classic branch protection (REST `branches/*/protection`) and
repository rulesets (GraphQL `rulesets`) — see
`clients/githubrepo/branches.go` (`rulesets` + `branchProtectionRules`
queries; rulesets are matched via `fnmatch` on `refs/heads/<branch>`). Older
Scorecard versions only read classic protection, which is why #725 keeps a
classic fallback even though the repo's declarative file uses the
`branchProtectionRules` schema from Microsoft's Kiota repositories.

Live state as of #725 (verify with the commands under Verification below):

| Branch / pattern | Mechanism | Where to edit |
| --- | --- | --- |
| `main` | Classic branch protection (REST `branches/main/protection`) | Settings → Branches → Branch protection rules, or `gh api -X PUT repos/{owner}/{repo}/branches/main/protection --input -` |
| `release/v*` (pattern, covers future `release/vX.Y` lines) | Repository ruleset `servicenow-sdk-go-release-protection` (id `21692927`) | Settings → Rules → Rulesets, or `gh api repos/{owner}/{repo}/rulesets/{id}` |
| `release/v1.0` (concrete branch that exists today) | Classic protection on the exact ref (same payload as `main` plus `required_linear_history: true`) | Same Branches settings as `main` |

`main` stays on classic because it is the single branch Scorecard always
evaluates (via `GetDefaultBranch`) and classic is readable via
`RefUpdateRule` even with a non-admin `GITHUB_TOKEN`. `release/v*` must be a
ruleset because classic has no wildcard — it only protects exact branch
names. The ruleset also covers future maintenance lines without a per-branch
PUT at cut time.

Both mechanisms enforce the same guarantees as the declarative file; keep
them in sync when that file changes.

## Ruleset definition (declared in `.github/policies/`)

`servicenow-sdk-go-branch-protection.yml` declares two branch-protection
rules using the `resource: repository` / `configuration.branchProtectionRules`
schema:

| Rule | Branches | Guarantees |
| --- | --- | --- |
| trunk | `main` | PR + 1 CODEOWNERS approval, stale-review dismissal, conversation resolution, no deletion/force-push |
| maintenance lines | `release/v*` | same as trunk **plus required linear history** |

Both require only universally reporting status checks (`Check Branch Name`,
`Check Linked Issue`, `Validate PR Title`, `CodeQL`) — path-filtered jobs
would sit pending forever on PRs whose paths they skip.

The table below is the human-readable spec the declaration encodes; consult
it to review changes or apply the settings by hand. For `main`, the Settings
→ Branches UI maps one-to-one; for `release/v*`, use Settings → Rules →
Rulesets.

| Setting | Value |
| --- | --- |
| Targets | `main` (classic) and branches matching pattern `release/v*` (ruleset) |
| Bypass actors | Repository admin (`actor_id: 5`, `RepositoryRole`, `bypass_mode: always`) — emergency use only |
| Require pull request before merging | On |
| Required approvals | 1 |
| Dismiss stale reviews on new commits | On |
| Require status checks to pass | On (see below) |
| Require branches to be up to date | Off (`strict: false`) — repo contains autogenerated `VERSION`/`CHANGELOG.md` owned by release-please; `true` would force constant rebases |
| Require linear history | Off for `main`, **On** for `release/v*` (cherry-pick backports must stay one-to-one) |
| Block force pushes | On |
| Block deletions | On |
| Require conversation resolution | On |
| Require code owners review | On |

### Required status checks

Don't hand-enumerate check names at ruleset-creation time — a fresh
`release/vX.Y` branch has no runs yet, and GitHub only offers checks that
have already reported on the branch. Instead:

1. Cut the branch and open one throwaway PR against it.
2. Let `codeql.yml`, `branch-policy.yml`, and `pr.yml` report once.
3. Edit the ruleset and require the checks that appeared — exactly the four
   declared in `.github/policies/servicenow-sdk-go-branch-protection.yml`
   ("Check Branch Name," "Check Linked Issue," "Validate PR Title," "CodeQL.")
   Never add path-filtered jobs (the ci.yml build/test/lint matrix): they
   skip docs-only or workflow-only PRs, and a required check that never
   reports sticks "pending" forever, blocking every merge until an admin
   bypasses.

For classic protection the same four contexts are set via:

```json
{
  "required_status_checks": {
    "strict": false,
    "contexts": ["Check Branch Name", "Check Linked Issue", "Validate PR Title", "CodeQL"]
  }
}
```

### Classic payload reference

`main` (and `release/v1.0` with `required_linear_history: true`):

```json
{
  "required_status_checks": {"strict": false, "contexts": ["Check Branch Name", "Check Linked Issue", "Validate PR Title", "CodeQL"]},
  "enforce_admins": false,
  "required_pull_request_reviews": {"dismiss_stale_reviews": true, "require_code_owner_reviews": true, "required_approving_review_count": 1, "require_last_push_approval": false},
  "restrictions": null,
  "allow_force_pushes": false,
  "allow_deletions": false,
  "required_conversation_resolution": true,
  "required_linear_history": false
}
```

Ruleset `servicenow-sdk-go-release-protection` payload (GraphQL `rulesets` target `branch`, `refs/heads/release/v*`) mirrors this with
`deletion`, `non_fast_forward`, `required_linear_history`, `pull_request`, and
`required_status_checks` rules. The declarative file is still the source of
truth for review — the live payload above is its applied form.

## Scorecard alignment (why both mechanisms)

- **v5.5.0 detection:** `BranchProtection` raw probe calls `GetDefaultBranch` + `ListReleases` to enumerate branches, then for each does a GraphQL `rulesets` query (available with `contents: read`) plus a `branchProtectionRules` / `RefUpdateRule` query (admin for full data, non-admin for basic). Matching rulesets are merged onto the `BranchRef` in `branches.go:applyRepoRules`. Scorecard therefore scores **the live GitHub settings, not the file** — the file alone leaves the check at 0.
- **Historical gap:** pre-v5.5.0 Scorecard ignored rulesets entirely, so a ruleset-only setup still scored 0. #725 verified that v5.5.0 *does* detect rulesets (the release ruleset is visible at `gh api repos/{owner}/{repo}/rulesets` and in GraphQL `repository.rulesets`), but kept the classic `main` protection as the documented fallback for older scanners and non-admin-token runs (classic's `RefUpdateRule` path works without admin).
- **Score achieved:** after applying classic to `main` (and `release/v1.0`) plus the `release/v*` ruleset, Scorecard Branch-Protection is **8/10** on `v5.5.0` (`score is 8: branch protection is not maximal … required approving review count is 1 on branch 'main'`). Reaching 10 would require 2 reviewers and `enforce_admins: true` (Tier 4/5); the repo intentionally stays at 1 reviewer (Tier 4) and `enforce_admins: false` with a RepositoryRole bypass (Tier 5) to keep release-please and emergency admin flows functional — see #724 for the two-person-review follow-up.

## Verification

Run after any change to the declarative file or live settings:

```bash
# Classic — main
gh api repos/michaeldcanady/servicenow-sdk-go/branches/main/protection \
  --jq '{enforce_admins, required_status_checks, required_pull_request_reviews, allow_force_pushes, allow_deletions, required_conversation_resolution, required_linear_history}'

# Classic — existing maintenance branch
gh api repos/michaeldcanady/servicenow-sdk-go/branches/release/v1.0/protection \
  --jq '{required_linear_history, required_status_checks}'

# Ruleset — pattern
gh api repos/michaeldcanady/servicenow-sdk-go/rulesets \
  --jq '.[] | {id, name, enforcement, target, conditions}'

# GraphQL view Scorecard actually uses
gh api graphql -f query='{repository(owner:"michaeldcanady", name:"servicenow-sdk-go"){rulesets(first:10){nodes{name enforcement target}} branchProtectionRules(first:10){nodes{pattern}}}}'

# Scorecard itself (workflow_dispatch, then check code-scanning alert 18)
gh workflow run scorecard.yml --repo michaeldcanady/servicenow-sdk-go
gh api repos/michaeldcanady/servicenow-sdk-go/code-scanning/alerts/18 \
  --jq '.most_recent_instance.message.text'
```

Expect `BranchProtectionID` to be `score is 8` (or `10` after #724), never `score is 0: branch protection not enabled for branch 'main'`.

## Bypass actors

The human spec lists a repository-admin bypass for emergency use. The
`branchProtectionRules` schema in the declarative file has no field for it —
bypass actors can only be configured when applying the live settings:

- Classic: `enforce_admins: false` already allows admins to bypass; no extra bypass actor field.
- Ruleset: `bypass_actors: [{"actor_id": 5, "actor_type": "RepositoryRole", "bypass_mode": "always"}]` (role `5` = Repository admin). The declared file is therefore the source of truth for everything except bypasses; record any bypass grant here in this runbook when it happens.

## What workflows already cover (no admin action needed)

- `branch-policy.yml`: branch naming (`backport/…` heads are exempt as
  automation) and linked-issue checks now run on `release/**` PRs.
- `pr.yml`: PR title lint already targeted `main` and `release/**`.
- `codeql.yml`: analyzes `release/**` PRs too, so "CodeQL" can report on
  maintenance-line merges (a required check must first be able to appear).
- `ci.yml`: build/test/lint run for any PR touching Go paths, regardless of
  base branch; pushes to `release/**` were already covered.
- `labeler.yml` / `CODEOWNERS`: path-based and base-agnostic; the #658
  audit required no changes.

## Release automation rehearsal (must still function under protection)

Protection must not break `release-please`, `dependabot`, or backport
automation. Rehearse after any live change:

1. **Dry-run the declarative file:** `python3 -m json.tool .github/policies/servicenow-sdk-go-branch-protection.yml` — confirms schema parse.
2. **Open a throwaway PR** against `main` and against `release/v1.0` (e.g. `chore/rehearse-branch-protection (#725)`) and verify the four required checks report and the PR is mergeable only with 1 CODEOWNERS approval and conversation resolution. Close without merging.
3. **Backport label:** label a dummy `main` PR with `backport release/v1.0` and confirm `backport.yml` would fan out (check `Select existing target branches` log); no actual backport PR needed.
4. **Stable/maintenance release configs:** `stable-release.yml` (main) and `maintenance-label.yml`/`backport.yml` are branch-scoped and use `contents: write`/`pull-requests: write` — they push to `release-please--` branches and open PRs, never directly to `main`/`release/v*`, so `enforce_admins: false` plus the admin bypass keeps them unblocked. No `restrictions` (push allowlist) is set, so bot pushes are not denied.

If any job would have been skipped as `pending` forever (path-filtered `ci.yml` matrix), it must **not** be a required status check — see Required status checks above.

## Known gap

Direct pushes to `release/v*` bypass PR-event workflows entirely (nothing
runs, nothing posts) until the ruleset above blocks them. Apply the ruleset
**before** cutting the first maintenance branch — ADR 011 rule 3 assumes it.
Classic protection on existing `release/v1.0` already blocks direct pushes
there; the `release/v*` ruleset covers any future line without extra API
calls at cut time.
